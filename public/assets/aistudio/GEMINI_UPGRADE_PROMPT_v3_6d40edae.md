## 2. ПЕРВЫЙ ЭКРАН «ГЛОБАЛЬНАЯ КАРТА РОСТА»

Наверху: «Growth OS Kazakhstan — Атырау → Казахстан» и выбранный период «28.10.2026 — 25.01.2027» (редактируемые границы). Отдельно честная фраза «Стратегическая цель: лидерство в Казахстане. Это цель, не доказанный статус».

На первом экране показать **круглую прогресс-диаграмму** (SVG или React component, не картинку), со значением «ПОДГОТОВКА К ЗАПУСКУ: N%». Наружное кольцо — фактически выполненная подготовка, внутри — подпись и X/Y подтверждённых обязательных шагов. Цвет прогресса: 0–19% красный/коралловый (пока далеко до готовности), 20–49% янтарный (формирование), 50–79% фиолетовый/синий (в работе), 80–99% бирюзовый (почти готово), ровно 100% зелёный (подтверждённо готово). Не применять этот цвет к состоянию задачи без смысла; отдельные цвета статусов ниже. Цвет — дополнение к тексту, не единственный маркер.

**Важно: ТРИ РАЗНЫХ ЧИСЛА, не один мифический «успех».**
1. *План выполнен*: процент подтверждённых обязательных шагов и подшагов. Прозрачно описать знаменатель, веса, исключения.
2. *Коммерческий результат*: оплаченные клиенты/выручка/кол-во демо — из реальных CRM-сделок и операций, никаких фиктивных чисел.
3. *Готовность к масштабированию*: отдельная шкала по обязательным milestone gates (продукт, юридическая готовность, onboarding, поддержка, экономика).

Круги по 10–12 направлениям в виде горизонтально прокручиваемой мини-сетки/карусели. Нажатие на круг → экран проекта → этапы → список задач → подробная карточка. Примеры направлений: Таргет Instagram, Atyrau Hub, Atameken/Damu, Партнёрская сеть, Торговые, Локальная известность, Клиенты и отзывы, Компания и договоры, Резидентство/офис, Product Engineering, Финансы/хостинг, Выход в другие города. Дублирующиеся проекты объединить в одну иерархию, не терять источники.

Цветовой словарь статусов:
- **Серый** — «Не начато», 0% прогресса.
- **Синий** — «Подготовка», хотя бы один подтверждённый шаг.
- **Фиолетовый** — «В работе» (процесс/исполнение).
- **Жёлтый** — «Ждём ответ / внешняя зависимость»; это не завершение.
- **Красный** — «Заблокировано», показать причину/ответственного.
- **Зелёный** — «Готово», все обязательные критерии проверены.
- «Перенесено», «Отменено» — отдельно; не считать готовым.

Добавить мини-легенду, которую можно раскрыть на мобильном.

Дашборд должен показывать Top-3 приоритетных шага на сегодня, дедлайны этой недели, что ждёт ответа внешних организаций, реальный бюджет vs траты и два маленьких прогресса «Я» и «Супруга». Не заставлять пользователя ежедневно пролистывать 237 задач.

## 3. ПОДРОБНАЯ КАРТОЧКА ЗАДАЧИ: ПРЕВРАТИТЬ ЗАПИСЬ В ПОНЯТНУЮ ИНСТРУКЦИЮ

В каждой из **237** задач должен быть полноценный план из `enriched_237_tasks.json`, а не шаблонная инструкция «выполнить конкретное действие». `verified_resources.json` — реестр только проверенных официальных источников. Импортировать по стабильным ID, расширить TypeScript `Task` необязательными полями, не нарушив старые данные:

- `goal`: зачем это делаем и какой эффект для бизнеса;
- `ownerRole`, `helperRole`, время, дата, срочность, зависимости;
- `guide.firstAction`: **первая конкретная инструкция на сегодня**;
- `guide.steps`: 3–7 пронумерованных, отмечаемых чекбоксами шагов (для каждого точная кнопка/канал/материал, если реально известны);
- `guide.example`: **пример**, явно обозначенный учебным, не реальная история;
- `guide.deliverable`: какой документ, звонок, контакт, видеоматериал, встреча, тест или запись должны появиться;
- `guide.qualityGate`: критерий, чтобы не поставить «готово» без результата;
- `links[]`: «Открыть официальный сайт», «Позвонить», «Написать письмо», «Открыть реестр» — только по существующим подтверждённым URL, телефон/email и только когда они относятся к задаче;
- `contactVerification`: «официально подтверждено / найдено, перепроверить / пока неизвестно». Если телефон отсутствует — явно показывать «Уточнить контакт», НЕ выдумывать;
- `draftMessage`: черновик делового письма или скрипт звонка там, где нужен контакт; с кнопкой «Скопировать»;
- `templates`: содержимое one-pager, FAQ, короткого скрипта, checklist подготовки зала, заявки на выступление, анкеты агента — там, где уместно;
- `evidence`: URL вложения, документ/заметка/фактическое подтверждение — user-entered;
- `nextAction`: что делать после задачи, включая дату повторного звонка;
- `sourceCheckedAt`: когда проверен внешний контакт и на какой странице;
- `notes` и журнал изменений.

Карточка на мобильном:
- Вверху заголовок, автор, срок, чип текущего статуса, кольцо прогресса по чек-листу (например 2/5 = 40%).
- Раздел 1: «Зачем это?» в 1–2 предложениях.
- Раздел 2: «Как сделать» — пронумерованные подробные шаги, чекбоксы.
- Раздел 3: «Контакты и полезные ссылки» — визуальные карточки, кнопки открытия системных `tel:`, `mailto:`, HTTPS.
- Раздел 4: «Готовый текст / пример» — копирование, редактирование.
- Раздел 5: «Что должно получиться» + поле подтверждения результата.
- Sticky footer: «Начать» / «Записать результат» / «Ждём ответ» / «Готово» (только при выполнении gate).

**Не все задачи имеют внешние контакты.** Для технического аудита, бюджета, планирования и отдыха показывать «Внешние контакты не требуются», а не мусорные ссылки. Внешние контакты из JSON — публичные организационные. Не добавлять людей из фантазии.

## 4. ЛОГИКА ПРОЦЕНТОВ: ЧЕСТНЫЕ И ПОНЯТНЫЕ ДАННЫЕ

Для задачи: `stepCompletion = completedRequiredSteps / allRequiredSteps × 100`; для 0 шагов — 0 и предупреждение «нужно уточнить чек-лист». Статус `done` доступен только если есть выполненный обязательный checklist + критерий `qualityGate` + запись подтверждения (ссылка, документ, объяснение) где это применимо. Если пользователь импортировал ранее завершённую задачу, не менять её автоматически и не требовать заново доказать задним числом — добавить флаг `legacyUnverified` и предложить подтвердить.

Для проекта: `projectProgress = Σ(weight_i × stepCompletion_i) / Σ(weight_i)` только по обязательным задачам; считать вес по P0=3, P1=2, P2=1, P3=0.5 либо явно задавать через milestone. **Для руководителя отдельно показать `doneTasks/requiredTasks`, чтобы 95% чек-листов не выглядели как 95% бизнес-успеха.** Если проект зависит от внешнего согласования, он не может показывать «Готово» до подтверждения. Дубликаты и задачи выходного дня исключить из показателей результата.

Визуальный статус проекта — производный: `blocked`, если критический gate заблокирован; `waiting`, если остались только внешние ответы; `ready`, если все обязательные gates выполнены; иначе `in_progress`/`preparing`/`not_started`. Показывать «Что мешает дойти до 100%» с 1–3 задачами. При каждом чекбоксе круг должен немедленно обновляться, затем сохраняться в storage. Тестами доказать, что прогресс не меняется от просмотра карточки и что статус «ждём ответ» не засчитывается как 완료.

Отдельно показывать «Планы» и «Факты»: `Цель: 10 клиентов`, `Факт: 0 подтверждённых` — не выводить фиктивные пилоты или примерные оплаты.

## 5. ЕЖЕДНЕВНЫЙ ЭКРАН «Я / СУПРУГА»

Два профиля: общий обзор и переключение «Мои задачи / Задачи супруги / Все». На главной 1–3 активных приоритета Founder и 1–2 Operations, приоритет по дедлайну, зависимости и эффекту. Для каждого: кнопка «Открыть инструкцию», время, ожидаемый результат. Просроченные задачи — отдельная вкладка «Требует пересмотра», не превращать весь экран в огромный список красных карточек. Следующий план по неделям, удобный календарь, перетаскивание срока с причиной и журналом.

Задачи супруга с высокой организационной конкретикой: адреса/телефоны Damu/Atameken, шаблоны писем, список документов, куда обращаться. Для Founder технические задачи: тестовые шаги, ожидаемое поведение, критерий acceptance, никакого автоматического деплоя без его подтверждения.

Не переполнять календарь в выходные: отдых без KPI. Учитывать доступность 90 минут Founder и 35 минут Operations в обычный будний день по настройкам, превышение отмечать предупреждением, автоматически не менять сроки без подтверждения.

## 11. КОНКРЕТНЫЕ ТЕСТЫ ПРИЁМКИ

1. На чистой установке реальные сделки = 0 и реальные оплаты = 0; ни один seed не засчитан выполненным без подтверждения.
2. Пользователь отмечает шаг 1 из 4 в задаче → 25% именно задачи; соответствующий проектный круг изменился, данные сохранились после reload.
3. «Ждём ответ Atameken» — жёлтый, не 100%, не считается выполнением мероприятия.
4. Задача «Позвонить Damu» показывает реальный официальный номер, адрес, ссылку на источник, скрипт и критерий; по нажатию телефона открывается dialer, без автоматического звонка.
5. Задача «Atyrau Hub» не содержит выдуманного мобильного номера; предлагает уточнение координатора.
6. Отметка `done` требует чек-листа и результата, если задача результатная. После проверки реальный прогресс меняется только от пользователя.
7. Сегодняшняя дата правильно меняется на 29.10.2026 по часовому поясу Asia/Atyrau; дни плана рассчитываются из startDate, без хардкода.
8. Данные браузера не исчезают при обновлении; экспорт → очистка на тестовом устройстве → импорт восстанавливает структуру.
9. Существующие пользовательские `done`, `notes`, переносы и CRM сохраняются при обновлении; никакой принудительной перезаписи.
10. Ошибочный внешний URL обозначается как недоступный; нет вымышленного контакта под видом проверенного.
11. На смартфоне круги, вкладки и подробная карточка читаются без горизонтального скролла основного экрана.
12. «Нужна помощь» фиксирует заметку, но **не** говорит «уведомление отправлено» без реального канала доставки.
